# Divergences: CoorRe on Solana ↔ CoorRe on Hedera

Concepts reused from the Solana build keep their names, fields and meaning. This table lists every place where Hedera has to differ, why, and what stays the same. Each row needs the maintainers' approval before phase 2.

| Concept | CoorRe on Solana (devnet) | CoorRe on Hedera (specified) | Why it differs |
|---|---|---|---|
| Who holds the funds | The program's case account holds the escrow and pays out (`onchain/programs/coorre_anchor/src/lib.rs:91-100`, `186-206`) | The host's PESEscrowV3 holds the funds; CoorRe never holds or moves HBAR | On Hedera CoorRe enters a host that already has its escrow; taking custody would change the host's contract |
| Steps and roles | Four role keys sign every step: submitter, agent, rule engine, approver (`lib.rs:57-66`) | The host's submission is evidence, not a CoorRe step; CoorRe signs only the decision (ESCALATED → APPROVED, REJECTED, or AUTO_APPROVED by an agent within the limit) | The oracle's key belongs to the host; CoorRe answers only for the decision |
| Role key binding | The program compares the signer's public key with the role key stored in the case (`lib.rs:141`) | The contract compares `msg.sender` with the delegate accounts of the mandate; an ED25519 account calls as its long-zero address and an ECDSA account as its alias (probe P7). The key ↔ account link is read from the account (Mirror Node `/api/v1/accounts/{id}`) | EVM contracts see account addresses, not public keys |
| Same keys | Ed25519 keypair JSON files sign transactions and evidence | An Ed25519 key can control a Hedera account (probe P7), so a delegate can use the same key for the account and for the decision credential | No divergence in the key type; only in how the contract sees it |
| Mandate | The case stores `amount` and `autonomy_limit`; the limit gates AUTO_APPROVED (`lib.rs:148-150`) | A registered mandate (issuer, delegates, quorum, scope, validity, revocation) plus the same optional autonomy limit, gating AUTO_APPROVED with the same `MandateExceeded` | The host has a standing manager and many periods, so authority needs a scope and a validity; the limit semantics do not change |
| Mandate validity | None: a case is opened and decided | `validFrom`/`validUntil` against `block.timestamp`, and revocation | Required by the host profile |
| Previous-hash chain | Each anchor carries `prev_hash`; genesis is `case_id` (`lib.rs:142-147`) | Kept in the decision credential (`previousEvidence`, genesis = `case_id`); the contract stores the decision's `evidenceHash` and the period's `auditHash` | One CoorRe step per case on Hedera; the chain stays in the evidence |
| case_ref | `urn:coorre:case:<ref>` chosen by the operator | `urn:coorre:case:wata:<chainId>:<escrow>:<agreementId>:<periodId>` | The case is a host period, identified by the host's own ids |
| Anchor of each step | One `EvidenceAnchor` account per step, owned by the program (`lib.rs:287-301`) | Contract state and event per decision, plus one message in the CoorRe HCS topic | Hedera has no program-owned accounts; HCS gives an ordered public log |
| Time recorded | `slot` and `unix_ts` from the Clock sysvar (`lib.rs:161-162`) | `block.timestamp` of the decision and the HCS consensus timestamp of its message | Hedera exposes both; HIP-415 defines the first (probe P2) |
| Trust anchors in the verifier | The expected program id (ADR-002) | Chain id, CoorRe contract address, escrow address, topic id (ADR-006) | One more source of record (the topic) and the host's contract |
| Verifier reads | Raw account bytes with owner and discriminator (`coorre-verify/src/verify.rs:55-60`, `416-546`) | Contract results, logs and topic messages from the Mirror Node | Different ledger model; checks 1, 2, 3 and 7 do not change |
| Rent | The amount must cover a rent-exempt payee (`lib.rs:88-89`, `AmountBelowRentExempt`) and a payout must leave the case account rent-exempt (`lib.rs:211-225`) | No rent; the escrow handles payouts | Not applicable |
| Error names | `UnauthorizedActor`, `MandateExceeded`, `InvalidTransition`, `PrevHashMismatch`, `CaseClosed`, `RolesNotDistinct` (`lib.rs:339-361`) | The same names where the meaning is the same (`UnauthorizedActor`, `MandateExceeded`), plus `MandateNotActive`, `OutOfScope`, `AuditHashMismatch`, `AlreadyDecided`, `NotIssuer` | New checks need new names; shared checks keep theirs |
| Golden vectors | `offchain/crates/coorre-model/tests/vectors/rfc8785` and `w3c-vc-di-eddsa-b3` | The same vectors for the decision credential; Hedera adds vectors for `mandateId`, the HCS message and `case_ref` → `case_id` | JCS and eddsa-jcs-2022 are shared; the Solana account bytes (`devnet-bridge-smoke`) have no Hedera counterpart |
