# Security Notes and Threat Model (living document)

## Privileged roles
Creator/operator (opens and funds cases), submitter/payee, agent, rule_engine, approver. Four role keys must be distinct per case. Program upgrade authority: Playground wallet on devnet (backed up in .local/); a Squads multisig is a next step.

## Threats and controls
- Case squatting (someone opens our case_id first): CaseRecord PDA seeds include the creator.
- Separation of duties bypass (one key holding several roles): RolesNotDistinct.
- Rogue or compromised automated actor moving value above its mandate: MandateExceeded enforced on-chain; only the approver can take ESCALATED to APPROVED.
- Unauthorized actor or forged transition: role-bound signer checks; actor_kind derived on-chain, never trusted from input.
- Reordering or replay of evidence: prev_hash chain checked on-chain and off-chain.
- Forged evidence with a valid signature from an unrelated key: verifier check 4 binds proof key to the on-chain role key.
- Fake accounts in an audit bundle: verifier ignores receipts, checks account owner == program and content equality.
- Compromised or misconfigured rule engine anchoring an approval the rule would not give (the chain only enforces the amount): verification check 7 re-runs the rule named in the evidence, taken from the registry the verifier ships, over the digest-checked documents and compares state, decision and reasons; any rule the verifier does not ship, or a known rule with a different hash, fails instead of being trusted (ADR-004, ADR-005). Not covered: authenticity of the documents themselves and custody of the role keys.
- Dating evidence and decisions: `validFrom` is written by the signer, so the verifier ties it to the on-chain Clock stored in each EvidenceAnchor. Check 6 requires every evidence's `validFrom` to be within 300 seconds of its anchor's `unix_ts`, whatever role signed it. Check 7 also requires the evaluation date of every automated decision to be the UTC day of that `unix_ts` or the day before, and fails when the anchor is unavailable. Across the 35 recorded devnet anchors the distance is 1 to 5 seconds; 300 seconds covers a transaction that lands just before its blockhash expires (150 slots) after one retry, since the CLI gives the bridge 150 seconds and stops the bridge process after 180. Every evidence of a case must cite the rule of the SUBMITTED evidence (check 2).
- Rule substitution (a bundle naming a rule written by whoever is audited): the rule registry is a trust anchor shipped with the verifier, like the expected program id (ADR-002); rules are selected by id and version and must match the shipped hash (ADR-005).
- Bundle naming its own program: the expected program id is an input of the verifier (default: the CoorRe devnet deployment), never read from the bundle (ADR-002).
- Path traversal through artifact names: names are limited to 1-128 characters of [A-Za-z0-9._-] and cannot start with a dot, enforced in evidence validation and in verification check 1.
- Identity of role keys: the chain proves which keys acted; the verifier report shows the creator and the four role keys read from the case record so an auditor can match them to people or systems.
- Ambiguous JSON (parser differentials): evidence is parsed as I-JSON before canonicalization; duplicate member names and integers outside the IEEE 754 safe range are rejected.
- Signature malleability and weak keys: Ed25519 verification uses strict mode (non-canonical signatures and small-order keys rejected); multibase keys and proof values must be canonically encoded.
- Key confusion: a proof is only created when its verification method resolves to the signing key; verification resolves did:key only, so no network lookup can substitute a key.
- Escrow draining or rent violation: exact `amount` movements, rent-exempt minimum preserved, checked arithmetic, payee/refund accounts constrained to stored keys.
- Payout stuck at the end of a case (payee left below the rent-exempt minimum): open_case rejects any `amount` below the rent-exempt minimum of a zero-data account, read from the Rent sysvar at runtime (AmountBelowRentExempt).
- Supply chain: pinned versions, committed lockfiles, CI on every push.
- Secrets: keys only in .local/ (gitignored); never logged. `.gitignore` also covers `.env*` and `*keypair*.json` anywhere, and a test (web/verifier/test/repo-hygiene.test.mjs) fails if a tracked file holds a Solana keypair (a JSON array of 64 bytes) or if those patterns are dropped.
- Wrong network: the bridge refuses to send unless the RPC reports the devnet genesis hash, so no other cluster is reachable by accident.
- Key files: the bridge and the CLI refuse key files readable by group or others and keypairs whose public half does not match the seed; key material never appears in output or errors. The CLI spawns the bridge without a shell, with a cleared environment that carries only PATH and the COORRE_* settings.
- Bridge input: strict JSON members, canonical hex/u64/base58 parsing, validated before any network call; on open_case every role key must be on the ed25519 curve and none can be the program id, and the submitter (payee) must be a system account, checked with a read before sending; the bridge is spawned without a shell.
- Bridge transport: RPC URLs must use https (plain http only on 127.0.0.1, ::1 and localhost); output and errors carry only the RPC origin; the whole command has a deadline (COORRE_BRIDGE_TIMEOUT_MS, default 180 s when run alone, 150 s when the CLI runs it) and reports Timeout with any signatures already sent; confirmation polls over HTTP; a retry that finds its account already in use returns the receipt of the earlier attempt if it is confirmed; file-system errors carry the system code, never key content.
- Untrusted text in the CLI: the CLI validates `case_ref`, `case_record` and anchor addresses when it loads a bundle, and escapes control, bidirectional and invisible characters in everything it prints, so a bundle cannot rewrite the terminal or forge a PASS line. Case ids in `cases.json` are limited to letters, digits, `-` and `_`. The CLI reads only the public half of the creator key file.
- Browser verifier: bundle content is rendered as text only (no innerHTML or eval, enforced by a test); Explorer links only after base58 validation; the Content-Security-Policy is compared in full by a test: `default-src 'none'`, scripts from the page itself plus `wasm-unsafe-eval` for WebAssembly, styles, images and fonts from the page itself (IBM Plex, self-hosted under the SIL Open Font License), `base-uri 'none'`, `form-action 'none'`. The policy is set by a meta tag, so `frame-ancestors` does not apply, and GitHub Pages sends no X-Frame-Options header: the page can be framed by another site. `connect-src 'self' https:` is needed because the viewer chooses the Solana RPC; only public account addresses are sent, in one `getMultipleAccounts` call per verification (none when a snapshot is used) and one per RPC address for the dashboards, shown with the time of that read. Every account read, from the RPC or from a snapshot, must carry an owner and base64 data. A snapshot must state the format `coorre-devnet-snapshot/1` and the expected program and network; only a file byte-identical to the published `samples/devnet-snapshot.json` is labelled as the recorded devnet snapshot, and any other snapshot is labelled as accounts from a file the viewer provided, not read from the chain, with a verdict that is not shown as a plain pass. Theme, language and intro preferences stay in the viewer's own browser storage.
- Pages deployment: the build job runs with `contents: read` only; the deploy job, with `pages: write` and `id-token: write`, depends on the build and runs only for `refs/heads/main`; every action is pinned by commit SHA (enforced by a test).
- Offline verification from a recorded snapshot (`coorre verify --accounts`): the snapshot is a claim by whoever recorded it, so a pass proves agreement with the recorded accounts, not with the chain; the transaction signatures and slots in docs/evidence/devnet-snapshot/ allow an independent re-check. With `--accounts`, the CLI refuses a snapshot whose recorded `network_id` or `program_id` differs from the expected one; a raw recording without these fields is read, and the output says the network is not recorded. The capture script only calls read methods, refuses an RPC that does not report the devnet genesis hash, requires https (plain http only on loopback, for tests), evaluates every account and status before writing and refuses to overwrite the recorded snapshot on any missing, foreign or unconfirmed entry, writes atomically, times out each RPC call and records only the RPC origin, so an API key in the URL never reaches the repository. Attacks run against the recorded cases are in docs/evidence/ATTACK_MATRIX.md.
- Zcash memo (`coorre zcash-memo`): offline only, no keys and no network. A memo links a payment to an anchored decision; it is written by the payer and does not prove the payer followed the decision (docs/design/ZCASH_READINESS.md).
- Build supply chain of the verifier: wasm-bindgen pinned to `=0.2.128` in the crate; CI downloads the official CLI release and checks its pinned SHA-256 before use.

## Bridge dependencies (checked 2026-10-08)
- Single direct dependency, pinned: @solana/web3.js 1.99.0 (published 2026-09-08). Lockfile committed; installs use `npm ci` with install scripts disabled (bridge/.npmrc).
- uuid < 11.1.1 (GHSA-w5hq-g745-h8pq, via jayson): only `uuid.v4` is used, which the advisory does not cover; still overridden to 11.1.1, which keeps the CommonJS `v4` export jayson needs.
- stream-json <= 3.5.0 (GHSA-528h-pc64-c93x, GHSA-hqr4-qq8f-hg3x, GHSA-mjw6-4jj6-33hc, via jayson): no compatible patched release exists (3.x changed its module layout). The code is unreachable: @solana/web3.js imports only `jayson/lib/client/browser`, and stream-json is loaded only by `jayson/lib/utils.js`. A runtime test (bridge/test/deps.test.mjs) fails if stream-json is ever loaded. CI fails on any high or critical advisory.

## CoorRe on Hedera (testnet, and a local Solo network in CI)
- Threat model, controls and the test behind each one: docs/hedera/THREAT_MODEL.md. Specification: docs/hedera/SPEC.md; execution path: ADR-007.
- Mandate contract (hedera/contracts/CoorReMandateGate.sol), deployed on Hedera testnet and verified on Sourcify: its source and hedera/contracts/IPeriodEscrow.sol are pinned by SHA-256 (hedera/lib/frozen.mjs), and hedera/test/frozen.test.mjs also pins the compiled runtime with immutables and metadata set aside. `npm run check:protections` removes each of its protections in turn (one entry per guard, 50 today) in a copy outside the repository, refuses to start if a pinned source changed, and requires at least one failing test for each; a run that does not compile or fails without a failing test counts as inconclusive and fails the check. hedera/test/protection-check.test.mjs fails if a guard has no entry, and hedera/test/docs.test.mjs fails if the threat model cites a test that does not exist. CI runs all of this on every push and pull request (job hedera); the Solo network run (hedera-solo.yml) runs on main and on pull requests that change hedera/.
- Host requirement: the gate keys a period's votes by agreement, period and auditHash, with no round number, so the host's escrow must refuse an auditHash it has accepted before (the reference escrow reverts with AuditHashUsed). A host profile states it in evidence.auditHashUnique with a host-code source, and the profile test requires it. A round number in the period key is a next step for a future deployment of the gate.
- Host data: the public repository carries the generic engine and a fictitious example only. Host profiles, addresses, accounts, mandates and deploy records live in the host's private environment; the testnet deploy script refuses configuration or record paths inside the repository, links included, and refuses a CoorRe operator that is any of the host's accounts. HCS messages carry ids and hashes only, built by one function that refuses any field outside the message's kind.
- Dependencies of hedera/ (checked 2026-10-26): runtime, @hiero-ledger/sdk 2.90.1 only, with ws overridden to 8.21.3 (GHSA-58qx-3vcg-4xpx, GHSA-96hv-2xvq-fx4p, via ethers in the SDK). Dev tools: hardhat 3.21.0 and ethers 6.16.0 (integration test only). Hardhat telemetry is on by default in an interactive terminal (`telemetry-permissions.ts` in NomicFoundation/hardhat), so every hedera/ script and CI job set `HARDHAT_DISABLE_TELEMETRY=true`. Accepted for dev tools only: zod 3.25.76 (GHSA-mrhx-c7xc-m3w5, high), required as `^3` by hardhat with no compatible fixed release; it validates only this repository's Hardhat configuration. CI fails on high or critical advisories of the runtime dependencies (`npm audit --omit=dev`) and reports the dev tools as a warning. Lockfile committed; install scripts disabled (hedera/.npmrc). Solo 0.94.0 is installed in CI from its npm tarball, checked against a pinned SHA-512; the GitHub token reaches only the network deploy step.
- Testnet: bytecode goes to the SDK as hex text only; fees are capped at 20 HBAR per transaction and at 40 HBAR for the gate's ContractCreate, both printed in the deploy plan; nothing is spent without `--confirm-spend`. Key files readable by group or others are refused before they are read. The deploy record is written after the gate, after the log topic and at the end, so a rerun resumes instead of deploying again; the log key file is never overwritten, and a Sourcify failure is kept in the record as an error.

## Declared limitations
Devnet only; custodial demo keys; no verifiable build; no fuzzing of the Solana program or the off-chain core; simulated agent (no LLM); public RPC rate limits; secret key bytes are not zeroed in memory after use.

The autonomy limit, the four role keys and the rule are chosen by whoever opens the case: the limit is fixed per case at open_case, public in the case record and checked by the verifier, but it is not enforced against the creator. A policy account under another authority or a multisig, or the approver's signature on open_case, is a next step.

Escrow has no exit outside AUTO_APPROVED, APPROVED and ESCALATED → REJECTED: a case that stops earlier, or an approver who never signs, keeps the amount in escrow with no expiry, cancellation or close, and the rent of case records and anchors is not reclaimed.
